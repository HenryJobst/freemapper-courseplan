# Purple Pen Sync (M3c) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `sync PROJECT` merges the project with its linked `.ppen` in both directions by a three-way merge against a stored sync base, lists conflicts with both values, and writes nothing until every conflict has a side.

**Architecture:** All three versions are compared in the same frame, the Purple Pen view: what the existing import makes of a `.ppen`. Base = import(base copy), theirs = import(linked file now), ours = import(export(project onto the base copy)). Because every side goes through the same reader, fit and rounding, Purple Pen's added defaults and the model's lossy mapping cannot show up as changes. The merge is a pure function in the courseplan crate (it works on the courseplan model). It classifies each field of each matched object as unchanged, ours, theirs, the same change on both sides, or a conflict. Then it applies theirs onto the project, and the existing patch export writes the result onto the current `.ppen`, with explicit `Deletions`. The CLI writes the `.ppen`, the project and the base copy in that order.

**Tech Stack:** Rust 2024; freemapper-core v0.7.0 (`freemapper-course`: `read_ppen`, `fit`, `write_ppen_patch`, `PatchOptions { delete: Deletions, ids_from_base }`); toml_edit project file; clap; rmcp; Fluent. No new dependency.

**Spec:** `docs/superpowers/specs/2026-11-08-freemapper-courseplan-design.md` §5.5a (also §5.5, §5.8, §7 "Sync", §9), ADR 0011, 0034, 0035, core ADR 0014.

## Decisions

Each one goes into ADR 0040 (the next free number) in Task 10.

- **D1 Base copy** *(Claude's call)*. A byte copy of the `.ppen` as the last sync left it, next to the project file: `X.courseplan.toml` → `X.courseplan.ppen-base`, i.e. the project's file name with `.toml` replaced by `.ppen-base`, or with `.ppen-base` appended when it does not end in `.toml`. The extension is not `.ppen`, so nobody opens it in Purple Pen by mistake. It is meant to be committed to git together with the project file. It holds whatever the `.ppen` holds, Purple Pen's `absolute-path` of the map included; the manual says so.
- **D2 Base record** *(Claude's call)*. The project gets an optional `[sync]` table: `ppen` (the link the base belongs to), `base_fnv1a64` (16 lowercase hex digits of FNV-1a 64 over the base bytes; this detects drift and is not a security measure), and `[[sync.decisions]]`. Format stays 1, because all of it is optional and additive (as with `ppen_id`, ADR 0034).
- **D3 Views and "changed"** *(Claude's call)*. A field is changed when its value in the Purple Pen view differs. Points are compared as integer µm (`(mm*1000).round()`), placements as hundredths of a degree and of a mm, climb in whole metres: the grid the import rounds to, so no tolerance on top of it. Purple Pen's added defaults (print areas, numbering, punch card, course appearance, labels, `hide-from-reports`, `absolute-path`) never reach the view (evidence: re-saving gives the same import; ADR 0035 byte-identical round trip).
- **D4 Fields** *(Claude's call)*. Merge is per field, not per object:
  - control: `code`, `kind`, `position`, description columns `c`..`h` (each column separately, so a symbol Purple Pen cannot hold survives an edit of another column);
  - special: `shape` (points + course list as course identities);
  - course: `name`, `stops` (identity sequence, start and finish included), `climb`, `print_scale`, `number` per (course, control, k-th visit) as the shown placement (course control's own, else the control's central one);
  - leg: event-wide per ordered pair of identities, `(bends, taped)` (Purple Pen keeps one leg per pair; the writer refuses two drawings).
  - Existence is the `Option` around every field: absent = deleted or not yet created.
- **D5 Pick rule** *(user, design §5.5a; Claude's call for the details)*. For base b, ours o, theirs t (each `Option`): `o == t` → unchanged if `== b`, else the same change on both sides; `o == b` → theirs; `t == b` → ours; otherwise conflict. That covers deletion on one side, added on both sides, and delete versus edit.
- **D6 Stop lists** *(Claude's call)*. When both sides changed `stops`, a diff3 over the identity sequences (LCS against the base, stable and unstable chunks). Changes that do not overlap merge. Overlapping changes that differ are one conflict on `course/<name>/stops`. A leg that no longer exists in the merged stops drops its changed bends with a note.
- **D7 Matching** *(user, design §5.5a: code/name, ids as second key; Claude's call for the order)*.
  - theirs↔base: Purple Pen id, then code, name or special id, and always only within the same kind (normal control or crossing point, start, finish, special kind).
  - ours↔base: the project's `ppen_id` only if that id is in the base, then code or name.
  - New objects on both sides: normal controls by code, courses by name, starts, finishes, crossing points and specials by kind and equal shape.
  - Ids that are not in the base are never trusted.
  - A Purple Pen id reused after a deletion matches as one changed object. That never loses an edit: if ours changed it, it is a conflict.
- **D8 Id hygiene** *(Claude's call)*. The event sent to the writer carries exactly theirs' id for each object matched to theirs, and `None` for new ones. Ours-deleted objects go into `PatchOptions.delete` by theirs' id. After writing, a `KeptObject` that the theirs import modeled means that the writer did not match it: refuse, write nothing (`SyncError::Unmatched`).
- **D9 Conflicts** *(user, design §5.5a: nothing overwritten until a side is picked; Claude's call: the whole sync waits)*.
  - While a conflict has no side, nothing is written except stored decisions. A partial sync would need a per-object base, which a byte copy cannot express.
  - A decision is `{ key, take = ours|theirs, fingerprint }`, where fingerprint = FNV-1a 64 of the conflict's rendered ours and theirs values. It is used only while that fingerprint still matches, and it is cleared by the next completed sync.
  - Delete versus edit is one conflict on the object key (`control/35`): ours or theirs is either "deleted" or the changed values.
  - Purple Pen deleting a course that has classes in the project is a conflict, because the classes would go with it.
- **D10 Data only courseplan holds** *(user, design §5.5a)*. Classes, starter counts, accepted findings, `print_area`, team, relay and score courses, marked-route specials and multi-point forbidden routes never enter the view, so the merge does not touch them. A course or special the export skips is reported via the export's `CourseSkipped`/`SpecialSkipped` notes ("not written to Purple Pen"). Renames from Purple Pen follow into accepted findings, leg refs and special course lists.
- **D11 Deletions** *(Claude's call)*. A control that a merged course still visits, or that any course of the theirs file visits (including the ones the import skips: variations, score), is not deleted. It stays, with the note `DeletionKept`. Core already has `Deletions`, so no core change is needed for that.
- **D12 Format gate** *(user, design §5.5a)*. Before anything else, the identity patch `write_ppen_patch(theirs, &read_ppen(theirs)?, &PatchOptions::default())` runs core's shape gate. An `UnknownVersion` refuses the sync, including in a dry run.
- **D13 Atomicity** *(Claude's call)*.
  - Order: `.ppen` (tmp + rename), then the project (with `base_fnv1a64` = hash of the new `.ppen`, decisions cleared), then the base copy, last.
  - Just before the `.ppen` write, the file is read again; if it changed since it was read (Purple Pen saved meanwhile), abort and write nothing.
  - Recovery: a crash after the `.ppen` write converges on the next sync (identical changes on both sides are not conflicts). A crash after the project write is repaired: if the recorded hash equals hash(theirs) but not hash(base), then base := theirs.
  - Any other mismatch, a missing base, or `sync.ppen` ≠ `sources.ppen`: sync without a base (empty base: nothing deleted, differing values conflict) with the note `BaseIgnored`.
- **D14 First sync** *(Claude's call)*. Without a base, project ids that exist in theirs with the same kind match, and then the start, finish and crossing point order fallback of `kth_renames` applies. `import --ppen` and `export --ppen` leave the base alone; the three-way merge copes with both.
- **D15 Interfaces** *(spec §5.8; Claude's call for flags)*.
  - CLI `sync PROJECT [--dry-run] [--take SIDE | --take KEY=SIDE]... [--json]`. A bare side applies to every open conflict and is never stored. `KEY=SIDE` is stored as a decision when other conflicts remain.
  - Exit codes: 0 synced or nothing to do; 1 conflicts remain or refused; 2 usage.
  - MCP `sync_ppen {project, dry_run?, take?}` and `resolve_sync_conflict {project, key, take}` (stores one decision and returns the remaining conflicts).
  - The editor's conflict panel belongs to the M4 editor plan (note only).
- **Core (freemapper-course, owner freemapper-print).** No change is required: `Deletions`, `ids_from_base`, `KeptObject` and the shape gate exist. One limitation: core's guard drops all event ids when one code or name contradicts the base (for example two codes swapped in one sync). A course renamed in the same sync then becomes new, and the old one is kept. D8's check turns that into a refusal. Proposal to freemapper-print via SendMessage, nothing changed before they agree: `PatchOptions::ids_first: bool` ("the caller vouches that the ids are this base's; match by id before code"). If they agree, a follow-up plan bumps the core tag; this plan does not depend on it.

## Review Focus

1. **Delete vs edit loses data.** A field changed on one side and the object deleted on the other must be a conflict, and nothing is written until it is resolved. Tests: `deleted_in_ppen_edited_here_is_a_conflict`, `deleted_here_edited_in_ppen_is_a_conflict`, `ppen_deleted_course_with_classes_is_a_conflict` (Task 3), `delete_vs_edit_writes_nothing` (Task 8).
2. **Id confusion between files.** A new courseplan control must never take over a theirs object that has the same, newly allocated or reused Purple Pen id, and ids from another file must never match. Tests: `ids_outside_the_base_are_not_trusted` (Task 2), `new_control_never_takes_over_a_fresh_ppen_id`, `writer_keeping_a_modeled_object_refuses` (Task 6).
3. **Base drift after a crash or a foreign base.** A crash between the writes must converge on the next sync, and a base that does not belong to the project must never cause deletions. Tests: `crash_after_ppen_write_converges`, `crash_after_project_write_repairs_base`, `foreign_base_is_ignored` (Task 7).
4. **Purple Pen's added defaults seen as changes.** A file re-saved by Purple Pen 4 without edits must sync to no change and leave the `.ppen` byte for byte. Tests: `purple_pen_defaults_are_no_change` (Task 6), `unrepresentable_symbol_survives_ppen_column_edit` (Task 3).
5. **Order-sensitive stop merges.** Inserts in different places both land, the same insert lands once, overlapping edits conflict, and the merge is symmetric. Tests: `diff3_exhaustive_properties`, `inserts_at_different_places_both_land`, `butterfly_visits_merge_by_position` (Task 1).

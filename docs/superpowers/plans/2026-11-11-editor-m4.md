# Browser Editor (M4) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `freemapper-courseplan edit PROJECT` serves a local course editor: the event on the left, the map with
the selected course or all controls in the centre, properties and findings on the right. Every change goes
through the same library operations as CLI and MCP and is saved to the project file at once.

**Architecture:** A localhost-only axum server in the CLI crate serves an embedded single-page app (plain ES
modules, no build step) and a JSON API. Mutations call the MCP tools' own bodies, split from their `#[tool]`
wrappers, so the editor adds no editing logic. The project file stays the source of truth: every operation
loads it, applies, saves atomically and returns a new revision. Undo restores whole-file snapshots. The map is a
`MapView` behind a small trait. A placeholder fills it until `freemapper-render` (core v0.9.0) ships, and the
editor draws the course overlay itself from Rust-computed geometry.

**Tech Stack:** Rust 2024; axum 0.8.9, rust-embed 8.13.0, getrandom 0.4.3 (the versions freemapper already uses
for `select`); tokio (features `net`, `time`, `signal` added); a new core crate `freemapper-web` (shared
local-server shell, D2); `freemapper-render` from core v0.9.0 (Stage 6); `freemapper-course` description symbols
and `number_offset`; Fluent; plain HTML/CSS/JS ES modules. No npm, no CDN, no JS framework.

**Spec:** `docs/superpowers/specs/2026-11-08-freemapper-courseplan-design.md` §5.8 (editor), §5.1 (map display
from the shared renderer), §3 (editor row, program language), §5.5a/§9 (conflict panel), §7, §8 M4. Also ADR
0005, 0008, 0013, 0022, 0023, 0024, 0040 and freemapper-print ADR 0005 and design §5.6.

## Decisions

Each decision goes into the ADR named with it. Marks: *(user)* decided by the user, *(agreed with …)* settled with
a sibling, *(Claude's call)* proposed here.

- **D1 Process model** (ADR 0042) *(Claude's call)*. `edit PROJECT [--port N] [--no-browser]`. The command loads
  the project first; a broken file stops it with the full CLI message and exit 1. It binds `127.0.0.1:N` (0 = free
  port), prints the URL as the only line on stdout, opens the browser (if that fails it prints a hint on stderr and
  keeps serving), reads nothing from stdin, and runs until Ctrl+C or the page's "Close editor" (`POST api/quit`).
  Exit 0. One project per process. Operations run one after another behind a `tokio::sync::Mutex` on
  `spawn_blocking`, the way the MCP server serialises its calls.
- **D2 Shared shell in core** (ADR 0042) *(Claude's call; owner is a user decision, Open question 1)*. freemapper's
  `select.rs` already has the token, host and origin checks, security headers, embedded assets and
  `open_browser`, and freemapper-print's M6 editor will need the same. Per the suite rule that shared code goes
  into freemapper-core, this lives in a new core crate `freemapper-web` (Task 1). Each app keeps its own routes.
- **D3 Security** (ADR 0042, amending ADR 0005) *(user for the base rules in ADR 0005; Claude's call for the
  additions)*. The base rules: bind 127.0.0.1 only, a random 128-bit token (32 hex digits) as the first path
  segment, a Host check (`127.0.0.1:PORT`, `localhost:PORT`), CSP `default-src 'self'; script-src 'self';
  style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; connect-src 'self'; frame-ancestors 'none'`
  (inline styles as in freemapper, because the renderer's SVG carries `style` attributes for blending),
  `X-Frame-Options: DENY`, `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. Added here:
  - every POST needs `Origin` equal to the page's origin, a non-safelisted `Content-Type` (`application/json`, or
    `application/octet-stream` for the import upload) and the header `X-Courseplan-Revision`. Cross-site pages
    cannot send a POST without a CORS preflight, and the server answers none;
  - **no path from the browser ever reaches the file system.** The API takes no file names. The server touches
    only the project file, its map (read), the linked `.ppen` and the sync base copy that the existing sync and
    export code chooses. The linked file is checked as `CoursePlanServer::sync_project` does: it must end in
    `.ppen` and must not be a symlink;
  - bodies are limited to 1 MiB, the import upload to `MAX_COURSE_FILE_BYTES`;
  - assets come only from the embedded set, so no path traversal is possible.
- **D4 Reuse, not new logic** (ADR 0043) *(Claude's call)*. Each MCP tool body moves into a plain
  method `fn <tool>_op(&self, req: <Params>) -> Result<Value, String>` on `CoursePlanServer`. The `#[tool]`
  wrapper calls it, and `CoursePlanServer::call_json(project, tool, args)` dispatches by name for the editor.
  The editor's operations are the MCP tools, with the same parameters (minus `project`, which the server
  injects), the same validation, the same JSON results and the same Fluent texts. MCP redaction (ADR 0023)
  applies to editor errors too. The person at the editor knows their own files, and the start-up load prints full
  messages. Export, import and sync use the CLI crate's functions (`export_iof_xml_file` split, `export_ppen_file`,
  `import_cmd::bring_in`, `sync_file`, `store_decision`), never new copies.
- **D5 Revision guard** (ADR 0043) *(Claude's call)*. `Revision` = `sync::base::fnv1a64` of the project file's
  bytes (16 hex digits). Every POST carries the revision the page last saw. If the file's revision differs, the
  answer is 409 with the current revision, nothing is written, and the page reloads its state and says so.
- **D6 Save guard against lost updates** (ADR 0044, closes the "project file not re-read" limit of ADR 0040)
  *(Claude's call)*. `ProjectFile` keeps the text it was loaded from, and `save()` re-reads the file first. If the
  file changed or disappeared, it refuses with `ProjectError::ChangedMeanwhile` and writes nothing. This fixes
  the race for CLI, MCP and editor alike. What remains is the window between that re-read and the rename.
- **D7 Undo/redo by snapshots** (ADR 0043) *(Claude's call)*. Each successful editor operation pushes
  `Step { label, before, after }` (whole file texts, at most 100 steps). Undo writes `before` atomically, but only
  while the file still equals `after`; redo works the other way round. On a mismatch (something else wrote the
  file) the history is cleared, nothing is written, and the answer is 409. Sync, import and export to the linked
  `.ppen` write more than the project file, so they clear the history. Inverse operations would need new logic
  per operation; snapshots need none and keep comments exactly.
- **D8 External changes** (ADR 0043) *(Claude's call)*. No file watcher (no new crate). The page polls
  `GET api/revision` every 2000 ms while visible and at once on `focus`. The answer holds the project revision,
  the map stamp (length, mtime) and the linked `.ppen` stamp. A new project revision reloads the state. A new map
  stamp rebuilds the server's map cache and reloads the map layer. A `.ppen` that changed since the last sync shows
  "Purple Pen file changed. Sync?" in the status bar.
- **D9 Front end** (ADR 0045) *(Claude's call)*. Plain ES modules (`<script type="module" src>`), hand-written
  CSS, no framework and no vendored library. freemapper's page is the same kind (vanilla JS); Leaflet is not
  needed because the map is one SVG view in page millimetres. Assets are embedded with rust-embed (`debug-embed`,
  so tests see the release set). The page loads nothing from the network. Map, overlay and handles share one
  root `<svg>`: the map as `<image href="api/map.svg?…">` at its page rectangle, the overlay as SVG elements in
  map mm under one `transform` built from the `MapView` mapping, so the two always line up.
- **D10 Layout** (ADR 0045) *(Claude's call: follows freemapper-print ADR 0005 and its design §5.6 so both editors
  feel the same; export in a menu is that design's user decision)*. Left: tree of courses, classes, controls and
  special objects. Centre: map with a toolbar (select, control, crossing point, special kinds, course mode).
  Right: properties of the selection above its findings. Top: a menu "Event" with export, import, sync and close.
  Bottom: status bar. Findings for the whole event open as a drawer from the status bar.
- **D11 Texts** (ADR 0045) *(user for German and English in Fluent, ADR 0022; Claude's call for the delivery)*.
  The UI's own words are `editor-*` messages without arguments, served by `GET api/texts` in the process language
  (`--lang`, `FREEMAPPER_LANG`, locale). Elements carry `data-text`, `data-label` (aria-label) or `data-title`.
  Anything with a number or a name comes from the server already formatted (findings, refusals, sync notes,
  status). A test keeps every `editor-*` message free of arguments. There is no language switch in the page:
  restart with `--lang`.
- **D12 Course symbols are drawn by the editor** (ADR 0046) *(Claude's call, recommended over waiting for the
  renderer)*. `GET api/overlay` returns circles, start triangles, finish circles, crossing points, legs (drawn
  parts from `course_legs`), number boxes and special-object shapes in map mm. The sizes come from `numbers.rs`
  (`overprint_sizes`, `circle_outer_radius_mm`, `number_box_mm`, scaled `base_scale / map_scale` as ADR 0030 and
  the placement do), and number boxes from core's `number_offset::offset_from_placement`. Numbers without a stored
  placement are shown where `auto_place(keep_existing = true)` would put them, drawn dashed. JS only draws what it
  receives. Reasons: each symbol must be its own element to select and drag, a drag must not wait for a
  re-render, and print's course layer arrives only after core v0.9.0. Parity: Rust tests pin the geometry to
  hand-computed values now. Once print's overprint is part of `RenderedPage`, a parity test compares both
  (Task 20), and a read-only "print preview" layer shows the renderer's own course symbols.
- **D13 Map view** (ADR 0046) *(user: the map comes from the shared renderer, no own minimal map; agreed with
  freemapper-print 2026-11-11 for the API)*. Trait `MapView` (Task 3). `PlaceholderMap` draws only the
  extent frame, a 10 mm grid and a centred note, never map content. `RenderMap` (Task 19) wraps
  `build::render_page(&doc, &PageSpec { print_scale: map scale, kind, show_sheet_objects: true })`,
  `svg::write_svg` for the viewport (rectangle plus 50 % margin on every side, re-requested 150 ms after
  pan or zoom stops) and `hits_at`. Text comes as glyph paths from the renderer, so no `@font-face` is needed
  (supersedes the Arimo note in spec §5.1).
- **D14 Number drags** *(Claude's call)*. In course mode a drag sets the course's number (`set_course_number`).
  With "for all courses" ticked in the properties it sets the central one (`set_control_number`). The drop point
  becomes direction and gap through `number_offset::placement_from_offset` on the server (`GET api/number-at`).
  A gap outside the rule range is stored and reported by `check`, as with the CLI.
- **D15 Import in the editor** *(Claude's call)*. The import reads an uploaded `.ppen` and does not change
  `sources.ppen`, because the server never learns a path. "Replace" is a checkbox. Export to Purple Pen goes to
  the linked file when there is one, otherwise it offers a download of a new file, and nothing is stored. IOF XML
  is a download.
- **D16 Column D proposal deferred** *(Claude's call; Open question 3)*. Spec §5.2 proposes column D from the map
  object. No symbol-to-description table exists yet. M4 lists the map objects at the control
  (`map_features_near`) next to the column D picker; the proposal is a later plan.
- **D17 Tests** *(Claude's call)*. CI stays Rust-only. Rust tests cover the API in-process
  (`tower::ServiceExt::oneshot` on the router), the binary end to end (spawned with `--no-browser`, raw HTTP over
  `TcpStream`) and the static assets (no inline script or handler, every `data-text` id in the catalog, size
  budget). The browser smoke checks at the end of each stage run locally with the `playwright` skill
  (`playwright-cli`); they are written down in the stage and reported in the stage's review, never committed as
  CI jobs.
- **D18 Release** *(user: release after a user-visible milestone; Claude's call for the timing)*. Every stage
  merges to `main`. Version 0.10.0 ships after Stage 6, the real map (Open question 2).

## Review Focus

1. **Another program writes the project while the page is open** (CLI, MCP, sync from a terminal, a hand edit).
   The editor never overwrites that change. A stale POST gets 409 and the page reloads. Tests:
   `stale_revision_is_refused_and_file_unchanged` (Task 8), `save_refuses_a_file_changed_since_load` (Task 6).
2. **A web page in the same browser calls the server** (CSRF, DNS rebinding, a guessed port). Foreign Host, a
   foreign or missing Origin on POST, a wrong token or a safelisted content type all get 403 and no write. Tests:
   `foreign_host_is_403`, `post_without_origin_is_403`, `form_post_is_403`, `wrong_token_is_404` (Task 1),
   `editor_routes_inherit_the_guard` (Task 2).
3. **Undo after someone else changed the file.** Undo must not throw away the other change. Test:
   `undo_after_external_change_is_refused_and_clears_history` (Task 8).
4. **The user breaks the TOML by hand while the editor runs.** State shows the error and edits are refused with
   the message; nothing is written until the file loads again. Test:
   `broken_file_blocks_edits_until_fixed` (Task 8).
5. **Zoomed far out on a large map.** The SVG stays within the renderer's budget, or the page shows "zoom in" and
   keeps working. No hang, no multi-MB response. Test: `oversized_view_is_413_with_message` (Task 19), with the
   placeholder version `placeholder_svg_is_small_at_any_zoom` (Task 3).
